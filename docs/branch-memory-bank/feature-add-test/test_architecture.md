# テストアーキテクチャに関する追加考察

## テスト・実装間の契約と整合性モデル

テスト駆動開発において、テストコードとプロダクションコードの間には明示的な契約関係が存在するのだ。この契約関係を「テスト・実装整合性モデル」と捉え、以下のような層構造で理解することができるのだ：

```
[テスト仕様]   ← 期待要件を表現
    ↓
[インターフェース契約] ← コンポーネント間の境界定義
    ↓
[実装ロジック] ← 具体的機能実現
```

テスト失敗のタイプをこのモデルで分類すると：

1. **契約不一致型失敗**：インターフェース定義が変更されたがテストが追従していない
2. **仕様解釈相違型失敗**：テストと実装で要件の解釈が異なっている
3. **実装未完成型失敗**：要件の実装が完了していない（本来のTDD的な失敗）

## テスト不一致のアーキテクチャ的アプローチ

現状のジェネレーターテスト不一致に対して、アーキテクチャ的に以下のアプローチが有効なのだ：

### 1. テスト比較粒度の再設計

```typescript
// 変更前：出力テキスト全体を比較
expect(summaryText).toContain('エンドポイント総数: 3');

// 変更後：意味的構造の検証に焦点
expect(parseOutput(summaryText)).toMatchObject({
  endpointCount: 3,
  methodDistribution: { GET: 2, POST: 1 }
});
```

### 2. 出力契約の明示的定義

インターフェース境界での契約を明示化するため、出力フォーマット仕様を独立したドキュメントとして定義し、テストと実装の整合基準とするのだ。

### 3. インターフェーステスト/ユニットテストの分離

- **インターフェーステスト**：契約の検証に特化（フォーマット、構造など）
- **ユニットテスト**：内部ロジックの検証に特化

この分離により、契約変更と実装変更のテスト影響範囲を限定できるのだ。

## テスト成熟度の段階的改善モデル

テストスイートの成熟度を段階的に高める道筋として：

1. **基本カバレッジフェーズ**：基本機能のテスト実装（現状）
2. **契約整合フェーズ**：テスト・実装間の契約整合性の確保（次ステップ）
3. **柔軟性向上フェーズ**：テスト比較粒度の最適化、契約変更への耐性強化
4. **持続可能性フェーズ**：テスト自動化、回帰テスト体制の確立

現在は「基本カバレッジ」から「契約整合」フェーズへの移行期であり、テスト失敗はこの移行プロセスの自然な現象と捉えることが適切なのだ。

## 整合性回復の技術的アプローチ

テストと実装の間の整合性を回復する具体的な手法として：

1. **スナップショットテスト導入**：期待出力をスナップショットとして保存し、変更時に差分確認

2. **構造比較への移行**：
   ```typescript
   // 出力テキストをパースして構造的に検証
   const parsedOutput = parseMarkdown(generatedContent);
   expect(parsedOutput.sections.summary.endpointCount).toBe(3);
   ```

3. **テストファクトリー導入**：
   ```typescript
   // モック生成を標準化
   const mockResult = createTestAnalysisResult({
     endpointCount: 3,
     httpMethods: { GET: 2, POST: 1 }
   });
   ```

これらの手法を組み合わせることで、テストの堅牢性と柔軟性を両立させることが可能になるのだ。
